# Clone a template into this app, accurately

This codifies the exact workflow used to turn a Canva "Birthday Event Website" design into the `birthday-cream-pink` template in this app — extraction, iterative pixel-matching, the "just give me the exact asset" fallback, and the final Next.js port. Follow it in order. Don't skip the verification phase — it's the part that actually earns the word "accurate."

## Phase 0 — Figure out what you're actually looking at, and ask for the right input

Not all inputs give you the same accuracy ceiling. If the user hasn't already given you the best available one, **tell them what would get a more accurate result and why**, rather than silently doing your best with a screenshot when something better was available. In priority order:

1. **Raw DOM/HTML dump — the single best input, ask for this first if the source is any web-based tool (Canva, Figma's web view, any editor with a browser tab).** Getting this is usually as simple as them selecting all the text/elements in that tab and pasting, or right-click → "View Page Source" / "Inspect" → copying the `<html>`. **Read it for embedded JSON, not just visible markup.** Design tools routinely inline a full scene-graph as a `<script>` JSON blob — exact per-element x/y/width/height (often as percentages of a known canvas size), rotation in degrees, hex colors, font family + weight + size + line-height, z-order, and even color-remap tables for recolored icons (`{"#48cfae":"#ffffff"}` tells you an icon's *rendered* color, which is not the same as its source-file color). This is ground truth — ​exact numbers, not estimates — and is what made the very first pass of a layout/color/font match accurate in one shot. Grep for `font`, `color`, `rotat`, hex patterns, and any large inline JSON before doing anything else with it.
2. **A live URL you can navigate to and inspect.** Nearly as good as #1 — you can read real computed styles and DOM structure directly instead of relying on what got pasted. Ask for this when the design is already published/hosted somewhere and there's no easy "copy the HTML" step.
3. **A full-page screenshot/PNG of the whole template, no DOM.** The fallback when neither of the above is available. You're doing visual analysis now: zoom into regions, name exact shapes (organic blob vs. true circle vs. N-point starburst vs. scalloped seal), estimate rotation angles from the tilt of text baselines, and describe colors precisely (don't say "pink," say "coral/salmon pink, warmer than a typical Barbie pink") rather than presenting a guess as a fact. Ask for the **highest-resolution, least-compressed** version available — a blurry or heavily-compressed screenshot makes color sampling and font identification meaningfully worse. Expect more correction rounds (Phase 2) with this input than with #1 or #2.
4. **A PNG crop of one specific decorative element — needed regardless of what else you have, whenever that element is real illustrated artwork.** Tiers 1–3 tell you layout, color, and typography accurately, but they cannot make CSS reproduce a hand-drawn sticker or an organically-bumped ribbon — that's raster/vector art, not a shape a browser can draw from a spec. The instant you (or the user) notice an element like that, ask specifically for a cropped image of *just that piece* — see Phase 3 for what to do with it once you have it.

**The best combo, and the one to steer the user toward:** tier 1 or 2 for the overall template (nails structure/color/type in one pass), *plus* tier 4 crops for any individual illustrated pieces spotted along the way. A tier-3 screenshot alone is workable but should be treated as a starting point you'll refine over several rounds, not a one-shot source.

**Gotcha when reading font-size out of tier-1 JSON/DOM: check for a nested `scale()` transform between the text and the number you're reading.** Design tools frequently render text at one "design" font-size inside a wrapper `<div>`, then scale that whole wrapper up to fit the final layout (e.g. a `<p style="font-size: 54px">` sitting inside a `<div style="transform: scale(2.62)">`, itself inside the element whose outer width/height you extracted for position). If you read the `<p>`'s font-size directly, you'll get a value that's too small by exactly that scale factor — the *true* rendered size is `font-size × scale`, and this mistake is easy to miss because the element still looks plausible in isolation and the bug only becomes obvious once you compare proportions against the reference (text renders uniformly smaller than the source, often dramatically so — a 2–3× miss is common). Verify it: multiply the wrapper's inner (pre-scale) box width by its scale factor and confirm it equals the outer box's width from the position data — if it matches, that same scale factor applies to every font-size read from inside that wrapper. Do this check for every text element up front, not just one, since the same tool typically wraps every text layer the same way.

Whichever you have, produce a first pass as a **standalone HTML/CSS/vanilla-JS prototype file** (`template-<name>-prototype.html` at the project root — this repo's own convention; look at the existing `template-*-prototype.html` files for the pattern) before touching any React/Next.js code. Prototyping in plain HTML is faster to iterate on and lets the user review it in a plain browser with no build step.

## Phase 1 — Classify every element, THEN build

Before writing any CSS, go through the source element by element and sort each one into exactly one of two buckets:

**Bucket A — exactly reproducible, build it directly:**
- Text (font, size, weight, color, alignment, rotation all come from Phase 0's ground truth). Check whether a multi-line text block was authored as several separate strings/paragraphs in the source JSON (an array with multiple entries — a real hard line break, reproduce it with one) vs. a single string that the source's own renderer auto-wrapped to fit its box (one array entry, no embedded break) — for the latter, don't hardcode where it wraps; let the browser wrap it naturally at the same box width, since forcing your own break point becomes visibly wrong the moment the font-size or box width is even slightly different from what produced the source's wrap. If the browser's wrap point still looks meaningfully worse than the source (e.g. splitting a phone number), that's a sign the box width or font-size is off, not a reason to hand-craft a break — fix the underlying number instead of patching around it.
- Flat vector/geometric shapes fully described by numbers you have: solid-color rectangles/circles, gradients, a starburst/notch shape you can compute via `clip-path: polygon(...)` (e.g. `x = 50 + r·cos(θ), y = 50 + r·sin(θ)` for evenly-spaced points), drop shadows, borders.

**Bucket B — backed by an actual image asset in the source. Do not approximate it. Ask for it as a PNG crop, named individually, before building anything for it.**
This is a data question, not a judgment call — if the source's own DOM/JSON shows this element as a raster/image layer (an `<img>` tag, a "RASTER" type entry, a media/file URL, an asset with its own licensing metadata), it goes in Bucket B, **regardless of how visually simple it looks.** A plain white card, a strip of tape, a soft drop shadow baked into a photo cutout — these *look* like something CSS could trivially redraw, but "looks simple" is exactly the trap: you cannot verify a hand-authored CSS shape is pixel-identical to an actual exported image without the image, and guessing "close enough" is what this instruction is specifically here to stop. Photographs (stock or customer) are the one exception — those become a `PhotoSlot`/placeholder per Phase 4, not a crop request, since real customer photos replace them anyway.

**How to ask for Bucket B elements:** list them out individually and specifically — by name/description and roughly where they sit in the design ("the white polaroid backing card behind the photo," "the washi-tape strip across the top," not a vague "send me anything else") — so the user knows exactly what to crop and send for each one. Ask for all of that pass's Bucket-B elements together in one message rather than trickling requests one at a time, but keep each one individually named so a batch of pasted crops can be matched back to the right element. Once you have a crop, follow Phase 3 to place it — never fall back to redrawing it in CSS instead just because the crop hasn't arrived yet; leave an obvious placeholder box and wait.

Only after Bucket B is either asked-for or (per Phase 3) received should you build Bucket A elements — layout, spacing, and composition using the exact numbers from Phase 0, not rounded-off approximations.

**Fonts** (their own case, not quite A or B): if the source uses a paid/proprietary font (Canva's own fonts — "Bugaki," "Garet," "BD Script," "Bright Sunshine," etc. — are not on Google Fonts, and hot-linking them raises a licensing question worth flagging explicitly), pick the closest free Google Font by matching category first (serif vs. sans, slab vs. humanist, script vs. print), then weight and character (rounded terminals? high contrast? geometric?). **Say so in a code comment** — "Yellowtail stands in for Canva's Bright Sunshine (not on Google Fonts, same licensing reasoning as the save-the-date prototypes)" — so nobody mistakes the substitute for the real thing later. (Occasionally the source font turns out to have a genuine free/open-source release under a slightly different name — e.g. "Be Vietnam" → "Be Vietnam Pro" — check before assuming a substitute is needed at all.)

Use plain CSS (a single `<style>` block, one shared set of CSS custom properties for the palette/fonts) — no framework needed at this stage.

## Phase 2 — Iterate against the reference, one correction at a time

After every edit, actually render it (open in the Browser pane, or serve it locally) and compare section-by-section against the source. When the user pushes back ("doesn't look perfect," "not the same"), **don't guess broadly what's wrong** — ask yourself specifically: is it the shape, the color, the font weight/style, the rotation, the position/overlap, or the spacing? Re-inspect the reference for that one attribute before touching code. Small, targeted fixes verified one at a time beat a big rewrite guessed all at once.

If your screenshot/preview tool itself is unreliable (stale frames, blank captures, a hidden preview pane) — this happens — **don't stop verifying, switch verification method.** Fall back to reading the DOM directly:
- `getBoundingClientRect()` on key elements to confirm real layout/positions
- computed styles (`getComputedStyle`) to confirm colors/fonts actually resolved
- `img.complete && img.naturalWidth > 0` to confirm images actually loaded
- `document.elementFromPoint(x, y)` + walking `parentElement` to confirm what's *really* rendered at a suspicious spot, before assuming a visual glitch is a real bug
- extracted text content (to confirm copy, ordering, and structure)

A screenshot that looks wrong is not proof of a real bug until you've cross-checked the DOM. Conversely, don't declare something fixed just because the code "reads right" — actually re-render it.

## Phase 3 — Placing Bucket-B elements once you have the PNG

Some elements are real illustration/artwork (a hand-drawn ribbon with organic wavy bumps, a specific ticket shape with a particular stroke, or anything else flagged as Bucket B in Phase 1) that CSS can only ever approximate. Whether you asked upfront (Phase 1's default now) or only realized partway through — **and also any time the user says "I want the exact same element" / "100% accurate" about something you did approximate** — stop trying to get closer with code and get the literal asset instead:

1. Ask for (or notice they've already pasted) a cropped image of just that element.
2. **Actively locate the actual file rather than asking the user to find it for you.** A pasted/attached image usually lands somewhere on disk even if no path was given in the chat: check the OS's default screenshot folder (e.g. `Pictures/Screenshots/`, sorted by most-recent), the `Downloads` folder (design tools often export there — look for the largest recent burst of similarly-named files if several images were pasted at once), and the OS clipboard directly (e.g. `Get-Clipboard -Format Image` in PowerShell) as a last resort. Match by recency and, if ambiguous, actually open the candidate file(s) and visually confirm before using one.
3. Copy the confirmed file into the project (following whatever asset convention the target codebase already uses), then **swap the CSS approximation for a real `<img>`** referencing it. From that point on, never re-derive that shape in code again — always reference the literal asset.
4. If the asset is meant to wrap arbitrary/dynamic text (e.g. a name-ribbon that needs to work for any customer's name, not just the one in the source), rename the asset generically (not after the specific example name in the source) and overlay the dynamic text on top at the correct baked-in rotation angle, matched to how the source rotated it.

## Phase 4 — Port the verified prototype into this app's Next.js template system

Do not invent your own structure — **research the existing sibling templates first** (an Explore/general-purpose agent pass is worth it): read a comparable existing `app/i/[slug]/_designs/*.tsx` component in full, plus `lib/types.ts` (the `Invite` shape), `lib/templates/registry.ts` (`TemplateEntry` / `TemplateFieldManifest`), `app/i/[slug]/page.tsx` (how a template gets picked), `CustomizeForm.tsx`/`CustomizePanel.tsx` (how fields map to the order form), and whether a matching `public/templates/<slug>/` asset folder convention already exists. Confirm whether an animation library is already a dependency before reaching for one.

Then, matching that convention exactly:

- **Component**: `"use client"`, default-exports `function TemplateName({ invite }: { invite: Invite })`. Local helper components for photo slots (real `<img>` if `invite.photo_urls?.[i]` exists, else a placeholder) and for any fixed decoration assets. RSVP form state + a real `supabase.from("rsvps").insert(...)` (never a fake client-only form once it's a real template) matching the exact field shape every sibling template uses. CSS as a single template-literal constant at the bottom of the file, injected via `<style>{CSS}</style>`, with a short unique class prefix (this repo's convention — these are unscoped global styles, isolated per-template by prefix and by the customize-page's iframe sandboxing).
- **Genericize hardcoded example content.** A source design built around one example person's name/age needs those swapped for real `invite.*` fields — and dropped entirely if the field doesn't exist in this app's data model (e.g. there's no `age` field; don't reintroduce removed functionality just because the source design had it — check for an explicit past-removal note before assuming a gap is an oversight).
- **Register it**: import + add an entry to `TEMPLATE_REGISTRY` in `lib/templates/registry.ts`, with a `TemplateFieldManifest` that's *actually verified* against which `invite.*` fields your component reads — not guessed.
- **Fonts**: add any new Google Font to the shared `<link>` in `app/layout.tsx` if it isn't already there.
- **Seed SQL**: this repo's convention is a manually-run SQL file per step, never auto-executed by you — write `supabase/seed-<slug>-template.sql` (registers the template row) and `supabase/seed-<slug>-demo.sql` (creates one demo invite). **Check for a third convention before calling it done**: some homepage/gallery surfaces need a demo invite explicitly flagged (e.g. `update invites set is_demo = true where slug = '...'`, see `flag-birthday-disco-demo.sql`) to get a live embedded preview instead of showing blank — grep for how existing templates achieve that gallery card treatment, don't assume the two seed files are the whole story. Running SQL against a shared/live database is the one part of this whole workflow you should NOT do yourself unless explicitly asked — write the files, tell the user what to run and in what order.
- **Animation**: reuse whatever motion idiom the codebase already has (e.g. an existing `IntersectionObserver`-based reveal component) rather than adding a new library. Keep it restrained: fade/slide reveals on scroll with a real stagger (30–80ms between siblings, a real cubic-bezier ease-out, not the default CSS easings), obvious press feedback (`scale(0.97)` on `:active`) on every button, hover-only flourishes gated behind `@media (hover: hover) and (pointer: fine)`, and a `prefers-reduced-motion: reduce` override that drops movement but keeps opacity fades. Only animate `transform`/`opacity`. If in doubt about a specific choice (easing, duration, whether something should animate at all), consult a design-engineering/animation-taste reference before guessing.

## Phase 5 — Final verification: prove it's actually accurate, then loop if not

Before calling this done:

1. **Typecheck and lint** the new/changed files (`tsc --noEmit`, project linter). Fix anything that surfaces.
2. **Render it with real data, without touching the live/shared database.** Build a throwaway local-only test route that imports the component directly with a hand-built fake `Invite` object, view it in a real dev server (not just the static prototype), confirm animations/interactions/images actually work, then **delete the scratch route** before finishing. Never seed fake rows into the real project database just to check your own work.
3. Re-run the same DOM-level checks from Phase 2 against the final component: every image's `naturalWidth > 0`, every text string present and in the right order, no console errors, no TypeScript/lint errors.
4. **Explicitly compare the finished result against the original source, element by element** — layout, colors, fonts (or documented substitute), shapes, spacing, text — the same checklist mentality as Phase 2, just run one more time end-to-end now that everything's assembled together, since integration can reveal mismatches that didn't show up piece-by-piece.
5. **If anything is still off, do not call it done — go back to Phase 2** (fix a Bucket-A CSS detail) **or Phase 1/3** (you missed classifying something as Bucket B — ask for that PNG now rather than approximating further) and repeat until every element checks out. State plainly to the user which parts you verified and how (e.g. "confirmed via DOM check, not a visual screenshot, because the preview pane was unreliable") rather than claiming success you didn't actually confirm.
6. Tell the user exactly what — if anything — is still their responsibility to do (e.g. running seed SQL themselves), and why you didn't do it for them.
